# Census 2017 source-place adjudication and implementation design

Status: project-lead design and native implementation approved on 27 September
2026. The corrected data preparation, analysis, output-contract tests, and
technical release checks completed; scientific and publication release remain
blocked. This decision supersedes the two held-case conclusions in the
[earlier audit](CENSUS_2017_SELECTION_AND_CODE_COMPARABILITY_AUDIT_2026-09-27.md),
not its broader selection cautions. Current aggregate results are documented

## Evidence and source hierarchy

The Dropbox workbook `2 data/Lista CCPP - Pedido INEI.xlsx` (last modified 5 March 2019; SHA-256 `11f90daceca445c0aa2d4bea8d84e8b5f355043e6e5a5d54d49668f812824933`) contains **889 unique requested CCPP codes**. All 807 codes in the delivered-source crosswalk occur in it; 82 requested codes do not occur in the delivered crosswalk. Its columns give the code and department/province/district, but no CCPP name. The INEI handoff `EnlaceCCPP-SISFOH_CPV.docx` (SHA-256 `f14ced074cbbb5b1c44a17c9ae40fa4842b1847dc9106b9aae6b5457f7073792`) says **889** in its opening description but **899** in its title and later paragraph. The observed workbook supports 889, not proof that a separate 899-code version never existed. The 807 delivered groups and 193,376 people are independently observed in the immutable delivery. Preserve both conflicting handoff statements in provenance; do not invent ten missing places.

The handoff describes 794 code matches plus 13 name-assisted matches and says SISFOH settlements with fewer than 150 residents could be grouped under a district code ending `9999`. In the delivered file, `ubigeo_ccpp` is the requested historical source code; `idccpp_sisfoh` is labeled “Identificador de centro poblado SISFOH”; `idccpp2019` is labeled as the CPV 2017 CCPP identifier; and `nomccpp` has only the generic label “nombre del centro poblado.” No located first-party field dictionary defines the last field more precisely or identifies the 13 name-assisted places. These omissions are recorded, not imputed.

`nomccpp` is unsuitable as an origin-assignment key: after a code merge to the SISFOH 2013 CCPP directory, only 4,451 of 193,376 delivered person rows have the same normalized name; 188,925 disagree. For example, the delivery labels 815 of the 836 people under `0306080001` “SAN CRISTOBAL,” while the SISFOH directory assigns San Cristobal its own code `0306080017`. The delivered `0307080030` group is labeled “CHECTASCCA,” although the 2007 and 2017 directories identify `0307080030` as Ccahuanhuire/Jahuanhuire. This is a field-use finding, not a claim about how INEI generated the column. Do not use `nomccpp` to transfer people between source codes.

### `0306080001` — Ranracancha: accept the source and canonical code

The request workbook includes `0306080001` but has an inconsistent district-code cell (`030605`); its ten-digit CCPP prefix and named district are Ranracancha (`030608`). [INEI's published district-code list](https://www.inei.gob.pe/media/MenuRecursivo/publicaciones_digitales/Est/Lib0952/Libro.pdf) independently identifies `030605` as Ocobamba and `030608` as Ranracancha. The project's 2007 directory and 2017 directory both name `0306080001` Ranracancha. A [2012 official VIVIENDA annex](https://spij.minjus.gob.pe/Graficos/Peru/2012/Agosto/09/RM-161-2012-VIVIENDA.pdf) independently prints the same ten-digit code, geography, and place name. The SISFOH 2013 directory has 836 people at that code, and the original SISFOH person-key roster has 836 exact source-code records; the INEI delivery has exactly 836 people under that code. The current RUV community `S03000445` is Ranracancha in the same district, and no other RUV community claims this code. Thus the historical source-to-RUV assignment and the canonical `0306080001` code are accepted. The contradictory `nomccpp` values do not rebut code-plus-person-roster evidence. The RUV registry also has the wrong six-digit district code for this one row; the pipeline corrects it under an exact-count guard before enforcing the unchanged CCPP-prefix/district consistency assertion. Both codes lie in province `0306`, so this does not change the selected RD geography.

### `0307080005` — Ancahuasi: quarantine the Cahuapirhua assignment

The request workbook includes `0307080005`. The project's 2007 directory, 2017 directory, [2017 OSIPTEL place list](https://www.osiptel.gob.pe/media/mufbu05f/res059-2017-cd_listacpp-sincobertura.pdf), and a [later official place-code list](https://cdn.www.gob.pe/uploads/document/file/7767540/6562480-resolucion-de-direccion-ejecutiva-000440-2025-de.pdf) identify it as **Ancahuasi**, Progreso/Grau. The SISFOH 2013 directory has 34 people there, the original SISFOH person-key roster has 34 exact source-code records, and the INEI delivery has exactly 34 records. All 34 have `idccpp_sisfoh=0307089999`, consistent with INEI's under-150 aggregation note, but their exact requested source code and person-roster match remain `0307080005`. The delivered `nomccpp` value “CCAHUANHUIRE” is not reliable origin evidence; Ccahuanhuire is a separately coded settlement (`0307080030`) and a separate RUV row (`S03000211`). RUV `S03000238` names **Cahuapirhua**, not Ancahuasi, and has no independently verified CCPP code. The existing `0307080005 → S03000238` crosswalk is therefore unsupported and must be quarantined. Do not reassign these 34 people to Ccahuanhuire or a different Cahuapirhua. A municipality also documents a Cahuapirhua in [Challhuahuacho/Cotabambas](https://munichallhuahuacho.gob.pe/documentos/ordenanza/2020/PLAN-OM-N%C2%B0-004-2020-MDCH.pdf); that same-name place does not establish the identity or code of RUV `S03000238` in Progreso/Grau.

## Binding analytical disposition

1. Preserve the immutable 193,376-person delivery and its 807 historical-source groups as the *raw source* and record the 889/899 discrepancy. Continue to report source coverage, person linkage, and movement observability as different selection stages.
2. Mark `0307080005` as quarantined in the executable source-to-RUV crosswalk, with no RUV ID. Exclude its **34 source people** from RUV-linked person, household, and CCPP analysis files while retaining their presence in raw-denominator and quarantined-count metadata. Keep RUV Cahuapirhua in the 5,712-community registry with Census 2017 outcomes missing, not zero.
3. Record `0306080001` as the verified canonical RUV code for `S03000445` in the existing RUV-code adjudication ledger, then retain its **836 source people** under that community. This should permit movement observability where a valid 2017 destination code exists; it does not make a nonlinked person a nonmigrant.
4. Regenerate the authoritative data preparation pipeline and all 2017-dependent main, heterogeneity, migration/mechanism, and publication-review outputs. Inspect the full sample-flow delta, exact key uniqueness, code collisions, merge cardinalities, treatment and RD-sample invariance, Census linkage stages, movement denominators, and outcome/estimate changes. Update aggregate metadata and manifests from the actual Stata run, not hand-calculated guesses. Mark old 2017 outputs stale until they pass validation; do not sync them to Overleaf or claim publication readiness before that check.
5. Do not use selection weights or bounds as a substitute for this identity correction. Remaining noncoverage and nonlinkage require explicit assumptions; a nonsignificant linkage diagnostic cannot establish ignorability. The 2017 migration estimand remains linked adults with valid canonical source and destination CCPP codes; it is not migration for all 2013 residents or all 2017 census residents.

The evidence adjudicates these two held assignments without an INEI field glossary or individual dated code-equivalence letter. Those documents would improve archival provenance, but their absence must not be disguised as direct confirmation. No broader name-based remapping or national cohort expansion is authorized by this decision.
